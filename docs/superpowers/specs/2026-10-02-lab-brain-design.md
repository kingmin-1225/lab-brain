# Lab Brain 설계 문서

- 작성일: 2026-10-02
- 상태: 설계 합의 완료, 구현 계획 전

## 1. 개요

연구실의 모든 자료를 폴더 구조 없이 수집하고, Karpathy의 LLM Wiki 패턴으로 LLM이 마크다운 위키를 관리하며, 그 위키를 근거로 질문에 답하는 연구실용 "세컨드 브레인" 웹 서비스.

```
[Raw 계층]    연구원이 올린 원본 자료 (수정하지 않음, 폴더 구조 없음)
     │ ingest
     ▼
[Wiki 계층]   LLM만 쓰는 마크다운 위키 (페이지 간 링크, index.md, log.md)
     │ query
     ▼
[Agent 계층]  위키를 근거로 답하는 에이전트 (+ 라이너 외부 검색)
```

**핵심 요구사항:** 여러 연구원이 동시에 사용해도 위키에 충돌이 생기지 않아야 한다.

**동시성 전략 요약:** 병합으로 충돌을 해결하는 대신, 구조적으로 충돌이 생기지 않게 한다.
- 모든 위키 쓰기는 하나의 작업 큐를 거쳐 worker 1개가 순서대로 처리한다.
- 작업 1개 = git commit 1개. 반영은 원자적이다.
- 읽기(에이전트, 웹 UI)는 커밋된 스냅샷만 보며, 큐를 거치지 않고 동시에 처리한다.

## 2. 결정 사항

| 항목 | 결정 |
|---|---|
| 형태 | 웹 서비스 (중앙 서버). 비개발자도 브라우저로 사용 |
| 위키에 쓰는 주체 | LLM만. 사람은 자료를 올리고, 질문하고, 수정을 요청함 |
| 접근 권한 | 연구실 구성원 전원이 모든 자료와 위키를 공유함. 로그인은 "누가 올렸는지/요청했는지" 기록하는 용도 |
| LLM | 외부 API. 공급자 교체 가능 (OpenAI 호환 인터페이스). 기본값은 라이너 Model API |
| 입력 형식 (1차) | PDF, 텍스트/마크다운, 이미지 |
| 라이너 활용 (1차) | ① 기본 LLM 백엔드(Model API) ② ingest할 때 논문 메타데이터 보강(Scholar Search) ③ 에이전트의 외부 검색 도구(Scholar/Web Search) |
| 에이전트 범위 | 최종 목표는 질의응답 + 산출물 생성. 1차는 질의응답만 |
| 아키텍처 | 마크다운 파일 + 내부 git + 단일 writer 큐 |

## 3. 아키텍처

```
[브라우저] ─ 업로드/채팅 ─▶ [API 서버] ──▶ Raw 저장소 (내용 해시를 파일명으로 사용)
                              │              Postgres (사용자, 자료 메타데이터, 작업 큐, 대화)
                              ▼
                     [Ingest Worker × 1] ── 위키 작업 공간에서 편집 ── 끝나면 git commit
                              │
[에이전트(질의응답)] ◀── 고정한 commit의 위키만 읽음 (동시 읽기 가능)
```

## 4. 데이터 모델과 저장소

### 4.1 Raw 저장소

```
raw/
  sha256_ab12….pdf
  sha256_cd34….png
  sha256_ef56….md      ← 붙여 넣은 텍스트, 저장한 답변, 정정 발언도 파일로 저장
```

- 파일명은 내용 해시(sha256). 같은 파일은 한 번만 저장되고 덮어쓰지 않는다.
- 폴더 구조가 없다. 분류는 LLM이 위키 페이지의 `type` 필드와 페이지 간 링크로 하고, `index.md`가 이를 type별로 묶어서 보여 준다.
- 원래 파일명, 올린 사람, 메모는 Postgres `sources`에 저장한다. 해시는 내부 식별자로만 쓴다.

### 4.2 Postgres

| 테이블 | 주요 필드 |
|---|---|
| `users` | id, 이름, 이메일 |
| `sources` | id, sha256, 원래 파일명, 형식, 종류(`upload` / `answer` / `correction`), 올린 사람, 올린 시각, 메모, 상태(대기/처리 중/완료/실패) |
| `jobs` | id, 종류(`ingest` / `edit_request` / `revert`), 요청자, 입력(source_id, 요청 문장 또는 되돌릴 job_id), 상태, 시도 횟수, 결과 commit 해시, 오류 메시지, 사용한 model, usage(토큰) |
| `chat_sessions`, `messages` | 질의응답 기록 |

작업 큐는 `jobs` 테이블로 구현하고, `SELECT … FOR UPDATE SKIP LOCKED`로 작업을 가져온다. 별도의 큐 시스템은 쓰지 않는다.

### 4.3 위키 (마크다운 + 내부 git 저장소)

```
wiki/
  SCHEMA.md       ← 위키 규칙 (페이지 type, 형식, slug 규칙, 출처 표기법). 사람이 관리함
  index.md        ← 전체 페이지 목록 + 한 줄 요약. type별로 묶음
  log.md          ← 작업 로그
  attention-is-all-you-need.md    (type: paper)
  transformer.md                  (type: concept)
  kim-minsu.md                    (type: person)
  …
```

- **하위 폴더를 두지 않는다.** 분류는 frontmatter의 `type`으로 한다.
  - 사용자는 웹 UI로 위키를 보므로 폴더가 주는 이점이 거의 없다.
  - 분류가 바뀌어도 파일이 이동하지 않아서 링크가 깨지지 않는다.
  - 이름공간이 하나라 중복 페이지가 바로 드러난다.
  - Karpathy 원문도 하위 폴더를 정해 두지 않았다.
- frontmatter 필수 항목: `type`, `sources: [source_id…]`
- 논문 페이지에는 라이너 Scholar에서 가져온 `authors`, `venue`, `citations`를 넣는다. 보강에 실패하면 `metadata: unverified`로 표시한다.
- `SCHEMA.md`에 slug 규칙(소문자-하이픈 등)과 "새 페이지를 만들기 전에 `index.md`에서 비슷한 이름을 확인할 것"이라는 지침을 넣는다.
- commit 메시지에 `job_id`를 넣어서 Postgres 작업 기록과 git 이력을 연결한다.

## 5. Ingest 흐름

```
① 업로드 (API 서버, 즉시 응답)
   해시 계산 → 이미 있는 해시: "이미 등록된 자료(언제, 누가)"라고 알리고 종료
            → 새 해시: raw/에 저장 + sources 행 생성 + ingest 작업 추가
   → UI에 큐 대기 순번 표시

② Worker가 작업을 가져옴 (worker 1개, SKIP LOCKED)

③ 전처리 (LLM 공급자와 무관하게 서버가 직접 처리)
   PDF   → 텍스트 추출, 그림이 많은 페이지만 이미지로 렌더링
   이미지 → vision 입력
   텍스트 → 그대로 사용

④ 라이너 Scholar 보강 (논문일 때만)
   제목으로 scholar 검색 → 저자, 학회/저널, 인용 수를 가져옴
   같은 논문 페이지가 이미 있으면 새로 만들지 않고 기존 페이지의 sources에 추가함

⑤ LLM 에이전트 루프 (라이너 Model API, 위키 작업 공간에서)
   컨텍스트: SCHEMA.md + index.md (공통 앞부분, 캐시 대상) + 전처리된 자료
   도구:     search_wiki / read_page / write_page
   할 일:    자료 요약 페이지 작성 → 관련 페이지 갱신 → 모순되는 내용 표시 → index.md, log.md 갱신

⑥ 검증 → commit
   검증: 모든 페이지에 type과 sources가 있는지, 링크가 실제 페이지를 가리키는지, slug 규칙을 지켰는지
   통과 → git commit (메시지에 job_id) → 읽기 쪽이 보는 위키가 새 commit으로 바뀜
   실패 → 오류 내용을 LLM에게 돌려주고 고치게 함 (최대 N회). 그래도 실패하면 작업 공간을 마지막 commit으로 되돌림

⑦ sources, jobs 상태 갱신 → UI에 "반영 완료, 바뀐 페이지 N개" 표시
```

- `edit_request` 작업은 ③과 ④를 건너뛰고 ⑤의 지시문만 다르다. ⑥은 똑같이 거친다.
- 라이너는 ingest에서 ④(Scholar)와 ⑤(Model API)에만 쓴다. 관련 외부 논문을 자동으로 위키에 넣지는 않는다. 위키는 연구실이 실제로 다룬 지식만 담는다.

## 6. LLM 인터페이스

### 6.1 공통 범위로 제한

LLM 호출은 OpenAI 호환 Chat Completions의 다음 범위만 쓴다.
- messages: 텍스트, `image_url`
- tools (`strict` 스키마), `tool_choice`
- `response_format` (`json_schema`)
- `stream`, `reasoning_effort`

`temperature`, `seed`, `stop`, 파일(PDF) 입력은 쓰지 않는다. 이 범위가 라이너 Model API가 지원하는 범위이자, OpenAI 호환 API들이 공통으로 지원하는 범위다. 그래서 설정(`base_url`, `api_key`, `model`)만 바꿔서 공급자를 교체할 수 있다.

### 6.2 라이너 Model API (`liner-mark-1.1`) 특성

- 엔드포인트: `https://platform.liner.com/api/v1` (OpenAI Chat Completions/Responses, Anthropic Messages 호환)
- 컨텍스트 1M 토큰, 출력 최대 65,536 토큰
- 이미지: 요청당 10장, 총 20MB까지 (PNG/JPEG/WEBP/HEIC/HEIF)
- 가격(100만 토큰당): 입력 $1, 출력 $5, 캐시된 입력 $0.10
- 질문 난이도에 따라 내부적으로 여러 LLM에 배분한다. **응답에는 어떤 모델이 처리했는지 나오지 않는다.**
- 파일 입력과 `temperature` 등은 지원하지 않는다.

### 6.3 설계 반영

- 작업 종류별(ingest / 질의응답)로 공급자와 모델을 따로 설정할 수 있게 한다. 기본값은 둘 다 라이너다. ingest는 `reasoning_effort: high`를 쓴다.
  - 이유: 라우팅이 불투명해서 ingest 같은 어려운 작업이 작은 모델에 배분될 수 있다. 품질이 부족하면 ingest만 다른 공급자로 바꿀 수 있어야 한다.
- 출력의 일관성은 `temperature` 대신 `strict` 도구 스키마와 ⑥의 검증 후 재시도로 확보한다.
- 작업마다 응답 `model`과 `usage`를 `jobs`에 기록한다.

## 7. 질의응답 에이전트

**원칙:** 에이전트는 위키를 직접 쓰지 않는다. 읽기와 검색만 하고, 쓰기가 필요하면 큐에 작업을 넣는다.

```
질문 입력
  ▼
[스냅샷 고정] 질문을 받은 시점의 마지막 commit 해시를 고정함
  ▼
[에이전트 루프] (Model API, 도구 호출)
  컨텍스트: SCHEMA.md 요약 + index.md + 대화 기록
  도구:
    search_wiki(query)     고정된 commit에서 전문 검색
    read_page(slug)        페이지 읽기
    liner_scholar(query)   외부 학술 검색 ─┐ 위키가 부족할 때만
    liner_web(query)       외부 웹 검색   ─┘ (사용자가 "외부 검색" 토글로 끌 수 있음)
  ▼
[답변] 근거를 두 종류로 구분해서 표시
  위키 근거 → 위키 페이지 → 그 페이지의 sources → 원본 자료(올린 사람, 날짜)
  외부 근거 → 라이너 결과의 제목, URL, 저자, 학회/저널
```

- 라이너는 Search API(검색 결과만 받음)를 도구로 쓴다. AI Search Agent(답변까지 생성)는 쓰지 않는다. 위키 근거와 외부 근거를 한 답변 안에서 섞으면서 출처를 구분해야 하기 때문이다.
- 외부 근거를 내부 지식처럼 표시하지 않는다.

### 7.1 쓰기로 이어지는 경로

1. **"위키에 저장" 버튼:** 답변과 근거 목록을 마크다운 Raw 자료(`sources.종류 = answer`)로 저장하고 일반 `ingest` 작업을 만든다.
2. **수정 요청:** 사용자의 정정 발언을 에이전트가 알아채고, "이렇게 수정 요청을 넣을까요?"라고 확인받은 뒤 정정 발언을 Raw 자료(`correction`)로 저장하고 `edit_request` 작업을 만든다.

이렇게 해서 "위키의 모든 내용은 `sources`의 어떤 행으로 거슬러 올라간다"는 규칙을 예외 없이 지킨다.

## 8. 오류 처리

### 8.1 업로드
- 지원하지 않는 형식, 크기나 페이지 상한 초과, 손상된 파일은 즉시 거절하고 이유를 보여 준다.
- 스캔 PDF(텍스트가 거의 없음)는 페이지를 이미지로 렌더링해서 처리한다. 요청당 이미지 10장 제한이 있으므로 페이지 상한을 더 낮게 둔다.
- 같은 파일을 다시 올리면 거절만 한다.

### 8.2 Ingest 중 LLM 실패
| 상황 | 처리 |
|---|---|
| 429 / 5xx | `Retry-After`를 따라 간격을 늘리며 재시도 |
| ⑥ 검증 실패 | 오류 내용을 LLM에게 돌려주고 고치게 함 (최대 N회) |
| 도구 호출 횟수나 토큰 예산 초과 | 중단 |
| 최종 실패 | 작업 공간을 마지막 commit으로 되돌리고 `failed`로 바꾼 뒤 이유를 기록. UI에 "재시도" 버튼 표시. 큐는 다음 작업을 계속 처리함 |

### 8.3 Worker 비정상 종료 (재시작할 때 복구)
- commit 전에 종료됨: 작업 공간을 되돌리고 작업을 다시 큐에 넣는다.
- commit 후, DB 갱신 전에 종료됨: git log에서 그 `job_id`를 가진 commit을 찾으면 `done`으로 처리한다(중복 반영 방지). 기준 기록은 git이다.

### 8.4 라이너 장애
| 상황 | 처리 |
|---|---|
| Scholar 보강 실패 | 실패로 보지 않음. 메타데이터 없이 진행하고 `metadata: unverified` 표시 |
| 외부 검색 실패 (질의응답) | 위키만으로 답하고 "외부 검색 실패"라고 알림 |
| 402 크레딧 소진 | 큐 전체를 일시 정지하고 관리자용 배너를 표시함. 크레딧이 충전되면 이어서 진행 |

### 8.5 잘못된 ingest 되돌리기
- 작업 이력에서 "되돌리기"를 누르면 `revert` 작업이 큐에 들어간다. 먼저 `git revert`를 시도한다.
- 이후 작업과 충돌하면, LLM이 해당 `source_id`를 출처로 하는 내용만 골라 지우는 `edit_request`로 전환한다.
- 누구나 요청할 수 있고, 누가 언제 되돌렸는지 기록한다.

## 9. 테스트 전략

1. **결정적 단위 테스트 (CI):** 해시와 중복 제거, 작업 상태 전이, ⑥ 검증기, git 계층(commit, 되돌리기, `job_id`로 commit 찾기)
2. **동시성 테스트 (가짜 LLM 사용):**
   - 업로드 20건을 동시에 보냄 → 전부 접수되고 하나씩 처리되며, 최종 위키에 20건의 출처가 모두 반영됨 (유실된 갱신 없음)
   - ingest 도중에 질문 → 에이전트가 반쯤 고쳐진 상태를 보지 않음
   - 같은 파일을 동시에 업로드 → Raw 1개, 작업 1개
   - worker를 각 단계에서 강제 종료 → 재시작 후 부분 반영 없음, 중복 반영 없음
3. **가짜 공급자:** 정해 둔 도구 호출을 순서대로 돌려주는 가짜 LLM, 429/402/타임아웃을 흉내 내는 가짜 라이너 Search
4. **LLM 품질 평가 (모델이나 프롬프트를 바꿀 때, 또는 매일 밤):** 샘플 자료 10~20건 + 질문/정답 사실 목록으로 다음을 측정한다. 정답 사실이 답변에 들어 있는지, 인용한 페이지에 그 내용이 실제로 있는지, 중복 페이지가 생기지 않았는지. 라이너와 다른 공급자를 같은 세트로 비교한다.
5. **라이너 계약 테스트 (API 키가 있을 때만, 적은 횟수로 실제 호출):** 응답 형식과 프롬프트 캐싱 동작 방식을 확인한다.

## 10. 범위

### 1차 범위
- PDF, 텍스트/마크다운, 이미지 업로드와 ingest
- 위키 열람 (웹 UI, type별 필터)
- 질의응답 에이전트 (위키 + 라이너 외부 검색, 위키에 저장, 수정 요청)
- 작업 이력, 재시도, 되돌리기

### 나중으로 미룬 것
- 산출물 생성 (보고서, 온보딩 문서, 발표 초안). 같은 도구 세트에 긴 문서 출력 형식만 더하면 된다.
- 오피스 문서(docx/pptx/xlsx), 코드/데이터 파일, URL 입력
- 외부 연동 (Slack, 이메일, Google Drive)
- Lint (라이너 Scholar로 지식 공백과 최신 후속 연구 찾기)
- Deep Research 요청 → 결과를 Raw 자료로 ingest
- 능동적 알림
- 사람의 위키 직접 편집
- 접근 권한 분리
- 임베딩 기반 검색 (위키가 커져서 index와 전문 검색으로 부족해질 때)
- 에이전트의 Raw 원본 읽기 도구 (`read_source`)
- 긴 자료를 나눠서 ingest하기
- 병렬 worker + 낙관적 병합 (처리량이 부족해질 때)

## 11. 확인할 것

- 라이너 Model API의 프롬프트 캐싱 동작 방식 (자동인지, 지정이 필요한지). 문서에 없으므로 계약 테스트로 확인한다.
- 페이지 상한 N, 검증 재시도 횟수 N, 도구 호출과 토큰 예산 수치는 품질 평가를 거쳐 정한다.
